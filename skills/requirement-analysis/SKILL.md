# 需求分析

## 概述

使用此 skill 将模糊、零散或不完整的需求转化为结构化、可评审、可开发、可测试的需求说明。重点关注业务目标、用户角色、使用场景、流程规则、数据约束、异常分支、权限边界、验收标准、依赖风险和开放问题。

当用户要求“补全需求”“完善需求”“分析需求”“拆用户故事”“生成验收标准”“评审 PRD”“找需求遗漏”时使用此 skill。

当用户没有直接提供需求描述、Jira ID 或 TM ID 时，先展示需求描述来源选项并等待用户选择：

```text
1. 手动输入
2. Jira
3. TM
```

当用户输入包含 `--jiraid <JIRA-ID>`、`jiraid=<JIRA-ID>` 或类似 `requirement-case --jiraid bank-123` 的命令式表达时，将 Jira issue 作为需求来源，先通过 jira MCP 服务获取需求详情。

当用户输入包含 `--tmid <TM-ID>`、`tmid=<TM-ID>` 或类似 `requirement-case --tmid tm-123` 的命令式表达时，将 TM 需求作为需求来源，先通过 tm MCP 服务获取需求详情。

当请求需要系统化补全、输出完整模板或覆盖多类需求缺口时，阅读 `references/requirement-auto-completion-guide.md`。

## 需求描述来源

触发需求分析 skill 时，优先识别用户是否已经给出来源：

- 已直接提供需求描述：按来源 `1. 手动输入` 处理。
- 已提供 Jira ID：按来源 `2. Jira` 处理。
- 已提供 TM ID：按来源 `3. TM` 处理。

如果来源不明确，必须先询问用户选择：

```text
请选择需求描述来源：
1. 手动输入
2. Jira
3. TM
```

来源处理规则：

1. 手动输入
   - 用户选择 `1` 后，提示用户直接在对话框中输入需求描述。
   - 拿到需求描述后直接执行需求分析和自动补全。
2. Jira
   - 用户选择 `2` 后，提示用户输入 `jiraid`。
   - 获取 `jiraid` 后调用 jira MCP 服务获取需求详情。
   - 获取成功后基于 Jira 详情执行需求分析和自动补全。
3. TM
   - 用户选择 `3` 后，提示用户输入 `tmid`。
   - 获取 `tmid` 后调用 tm MCP 服务获取需求详情。
   - 获取成功后基于 TM 详情执行需求分析和自动补全。

如果用户选择来源后没有提供对应描述或 ID，不要继续推断，应等待用户补充。

## Jira 输入

支持以下触发形式：

```text
requirement-case --jiraid bank-123
requirement-case --jiraid BANK-123
jiraid=BANK-123
```

处理规则：

1. 从用户输入中提取 Jira ID，保留用户原始大小写，同时在调用前允许转换为 Jira 常见大写格式，例如 `bank-123` -> `BANK-123`。
2. 优先调用已配置的 jira MCP 服务获取 issue 详情。可用时获取标题、描述、类型、状态、优先级、经办人、报告人、标签、组件、版本、父子任务、关联 issue、验收标准、评论和附件摘要。
3. 如果 jira MCP 服务提供多个工具，优先选择语义最匹配的 issue 查询工具，例如 `get_issue`、`jira_get_issue`、`issue_get`、`search_issue` 或等价工具。
4. 获取到 Jira 详情后，将 Jira 内容作为“已知信息”的来源，并继续执行需求自动补全、规则拆解、风险识别和验收标准生成。
5. 如果 Jira issue 不存在、无权限、MCP 未配置或工具不可用，不要编造需求内容。应说明 Jira 获取失败原因，并要求用户提供需求文本或修复 Jira MCP 配置。
6. 不要在输出中暴露 Jira Token、Cookie、认证头或内部连接信息。
7. 如果 Jira 评论或附件信息与描述冲突，应在“问题 / 待确认”中标注冲突来源。

## TM 输入

支持以下触发形式：

```text
requirement-case --tmid tm-123
requirement-case --tmid TM-123
tmid=TM-123
```

处理规则：

1. 从用户输入中提取 TM ID，保留用户原始大小写，同时在调用前允许转换为平台常见大写格式，例如 `tm-123` -> `TM-123`。
2. 优先调用已配置的 tm MCP 服务获取需求详情。可用时获取标题、描述、类型、状态、优先级、负责人、报告人、标签、模块、版本、关联需求、验收标准、评论和附件摘要。
3. 如果 tm MCP 服务提供多个工具，优先选择语义最匹配的需求查询工具，例如 `get_requirement`、`tm_get_requirement`、`requirement_get`、`get_issue`、`search_requirement` 或等价工具。
4. 获取到 TM 详情后，将 TM 内容作为“已知信息”的来源，并继续执行需求自动补全、规则拆解、风险识别和验收标准生成。
5. 如果 TM 需求不存在、无权限、MCP 未配置或工具不可用，不要编造需求内容。应说明 TM 获取失败原因，并要求用户提供需求文本或修复 TM MCP 配置。
6. 不要在输出中暴露 TM Token、Cookie、认证头或内部连接信息。
7. 如果 TM 评论或附件信息与描述冲突，应在“问题 / 待确认”中标注冲突来源。

## 工作流程

1. 识别输入来源：手动输入、Jira、TM、PRD、用户故事、接口说明或缺陷描述。
2. 如果来源不明确，先展示需求描述来源选项并等待用户选择。
3. 如果用户选择手动输入但尚未提供需求描述，等待用户在对话框输入需求描述。
4. 如果存在 Jira ID，先通过 jira MCP 服务获取 Jira 需求详情，并记录 issue key、标题、状态、链接和更新时间等来源信息。
5. 如果存在 TM ID，先通过 tm MCP 服务获取 TM 需求详情，并记录 tmid、标题、状态、链接和更新时间等来源信息。
6. 识别需求对象：产品模块、功能、页面、API、流程、角色、平台、版本范围和业务背景。
7. 提取已知信息：目标、用户、触发条件、输入、处理逻辑、输出、状态变化、约束和依赖。
8. 标注缺口：区分明确事实、合理推断、待确认问题，不把假设写成确定需求。
9. 自动补全需求：基于上下文补充常见但缺失的功能点、业务规则、边界条件、异常流程、权限和验收标准。
10. 拆解需求：将大需求拆成用户故事、功能点、规则列表、字段清单或接口契约。
11. 识别风险：指出歧义、冲突、依赖、不可测点、上线风险和需要产品确认的决策。
12. 产出结构化结果：让开发、测试、产品都能直接评审和执行。

## 需求自动补全规则

自动补全时应遵循：

- 用“建议补全”“推断”“待确认”明确区分信息来源。
- 优先补全高风险和高频缺口：角色权限、状态流转、字段校验、异常处理、数据一致性、通知、审计、兼容性。
- 不虚构具体业务政策、金额阈值、法律规则、第三方能力或公司内部流程；缺失时列为待确认。
- 对每条补全内容说明触发条件和预期结果，避免只写抽象概念。
- 如果补全会改变产品范围，明确标注为“范围扩展建议”。

## 输出规则

根据用户输入选择合适结构。常规需求分析优先输出：

1. 需求摘要
2. 来源信息
3. 已知信息
4. 自动补全建议
5. 业务规则
6. 异常与边界
7. 验收标准
8. 问题 / 待确认

如果用户通过 Jira ID 输入需求，“来源信息”应包含：

- 来源：Jira
- Jira ID
- 标题
- 状态
- 类型 / 优先级
- 经办人 / 报告人
- 版本 / 组件 / 标签
- 链接或可追踪引用
- Jira 获取失败原因，如果未能成功获取

如果用户通过 TM ID 输入需求，“来源信息”应包含：

- 来源：TM
- TM ID
- 标题
- 状态
- 类型 / 优先级
- 负责人 / 报告人
- 版本 / 模块 / 标签
- 链接或可追踪引用
- TM 获取失败原因，如果未能成功获取

如果用户通过手动输入需求，“来源信息”应包含：

- 来源：手动输入
- 输入摘要

如果用户提供的是用户故事，优先输出：

- 用户故事拆分
- 验收标准
- 规则与边界
- 依赖与风险

如果用户提供的是 API 或接口需求，优先输出：

- 接口目标
- 请求字段
- 响应字段
- 校验规则
- 状态码 / 错误码
- 权限与幂等性
- 待确认问题

## 质量检查清单

最终输出前检查：

- 业务目标是否清楚
- 用户角色和权限是否完整
- 主流程、分支流程、取消/返回/重试/超时是否覆盖
- 输入字段、默认值、必填/选填、格式、长度和边界是否明确
- 状态流转和不可逆操作是否明确
- 异常、空数据、重复数据、过期数据和不可用数据是否覆盖
- 通知、日志、审计、数据同步和外部依赖是否需要说明
- 验收标准是否可观察、可开发、可测试
- 是否存在需求冲突、范围不清或无法验证的描述

## 澄清策略

除非缺失信息会显著改变需求方向，否则不要先停下来提问。先基于明确假设继续分析和补全，并把关键不确定项放入“问题 / 待确认”。

如果缺失信息涉及核心业务规则、合规限制、计费规则、安全权限或不可逆操作，应优先提出问题，并说明为什么这些信息会影响需求设计。

## 语言

匹配用户使用的语言。如果用户使用中文，除非用户要求英文，否则输出中文。
