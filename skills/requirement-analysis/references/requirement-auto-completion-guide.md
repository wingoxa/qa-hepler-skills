# 需求自动补全指南

## 补全维度

使用以下维度检查并补全需求：

| 维度 | 需要补全的内容 |
| --- | --- |
| 目标 | 业务目标、用户价值、成功指标、上线范围 |
| 角色 | 目标用户、管理员、审核人、系统任务、外部系统 |
| 场景 | 主场景、替代场景、前置条件、触发条件、结束条件 |
| 流程 | 创建、查看、编辑、删除、提交、撤回、审核、取消、重试 |
| 规则 | 资格、阈值、计算、审批、唯一性、优先级、生命周期 |
| 数据 | 字段、类型、必填、默认值、格式、长度、枚举、关联关系 |
| 权限 | 登录态、角色、所有权、租户隔离、可见性、操作权限 |
| 状态 | 草稿、待提交、待审核、通过、拒绝、失效、归档及合法流转 |
| 异常 | 空数据、重复数据、过期数据、无权限、网络失败、第三方失败 |
| 通知 | 站内信、邮件、短信、推送、回调、通知触发和接收人 |
| 审计 | 操作日志、变更记录、审批记录、失败记录、追踪 ID |
| 兼容 | 历史数据、老版本客户端、导入导出、迁移和灰度 |
| 验收 | 可观察结果、数据落库、接口响应、页面状态、消息提示 |

## 自动补全模板

可按需使用以下结构：

| 类别 | 补全内容 | 类型 | 理由 | 待确认 |
| --- | --- | --- | --- | --- |
| 权限 | 仅资源创建人和管理员可编辑记录 | 推断 | 涉及数据修改，通常需要所有权限制 | 管理员角色范围 |
| 边界 | 名称字段应限制长度并禁止纯空格 | 建议补全 | 避免无效数据和展示异常 | 最大长度 |

`类型` 建议使用：

- `明确需求`：用户已提供的信息。
- `推断`：基于上下文高度可能成立的规则。
- `建议补全`：为提升完整性、可用性或可测性提出的建议。
- `范围扩展建议`：可能增加开发范围的增强项。
- `待确认`：不能可靠推断，必须由业务或产品确认。

## 用户故事拆分

拆分用户故事时优先使用：

```text
作为 <角色>
我希望 <完成某个动作或目标>
以便 <获得业务价值>
```

每个故事应具备：

- 独立价值：可以单独评审和验收。
- 明确边界：包含和不包含的内容清楚。
- 可测试结果：可以通过 UI、API、数据或通知观察。
- 依赖说明：依赖的配置、数据、角色或外部系统明确。

## 验收标准模式

优先使用 Given / When / Then：

```text
Given <前置条件>
When <用户或系统执行动作>
Then <可观察的结果>
```

验收标准应覆盖：

- 正向路径
- 必填校验
- 权限限制
- 状态限制
- 异常反馈
- 数据持久化
- 通知或回调
- 回归影响

## 常见遗漏问题

需求分析时主动检查：

- 谁可以执行该操作，谁只能查看，谁完全不可见？
- 操作是否可以撤销、取消、重复提交或重试？
- 数据保存失败、第三方服务失败或网络超时时如何处理？
- 是否需要防重复、幂等、并发冲突处理？
- 历史数据和已存在用户是否受影响？
- 是否需要日志、审计、导出或通知？
- 错误提示由前端、后端还是第三方返回？
- 是否存在灰度、开关、配置项或运营后台需求？
- 移动端、不同语言、时区、货币或无障碍是否影响功能？
- 哪些内容属于当前版本范围外？

## 最终输出建议

大型需求可输出：

1. 范围
2. 角色与场景
3. 主流程
4. 自动补全需求
5. 业务规则
6. 字段与数据
7. 权限与状态
8. 异常与边界
9. 验收标准
10. 风险与待确认问题

小型需求可输出：

1. 需求摘要
2. 自动补全建议
3. 验收标准
4. 待确认问题
