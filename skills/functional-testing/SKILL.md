# 功能测试

## 概述

使用此 skill 将产品或工程上下文转化为可执行的功能测试覆盖。重点关注用户可观察的行为、业务规则、状态流转、权限、校验、错误、集成和回归风险。

当请求需要更广泛的覆盖、可复用的测试矩阵或结构化输出模板时，阅读 `references/test-design-guide.md`。

## 工作流程

1. 识别被测对象：功能、页面、API、流程、角色、平台和发布范围。
2. 提取明确需求并推导可测试行为。标注假设，不要把假设隐藏在用例中。
3. 将覆盖拆分为正向路径、反向路径、边界值、状态变化、权限、数据变化、错误处理、兼容性和回归检查。
4. 按用户影响、业务风险、使用频率、集成复杂度和缺陷可能性为用例排序。
5. 产出简洁、可执行的测试用例，包含稳定的标识符和清晰的预期结果。
6. 指出会阻碍可靠测试的需求缺口。

## 输出规则

除非用户要求其他格式，否则优先使用表格。

在有帮助时包含以下字段：

- `ID`
- `优先级`
- `场景`
- `前置条件`
- `步骤`
- `测试数据`
- `预期结果`
- `类型`

步骤应以行动为导向且可验证。避免使用“工作正常”这类模糊的预期结果；应写明可观察的 UI、API 响应、数据持久化、通知、权限结果或错误信息。

## 覆盖检查清单

最终输出前考虑以下类别：

- 正向路径和常见用户流程
- 必填字段和选填字段
- 输入校验、格式校验、长度限制和边界值
- 空数据、重复数据、过期数据、禁用数据、已删除数据或不可用数据
- 创建、读取、更新、删除、取消、重试、刷新和导航行为
- 角色、权限、所有权、租户和可见性规则
- 状态流转、幂等性、并发和中断后的恢复
- 搜索、筛选、排序、分页、导出、导入和批量操作
- 客户端、服务端、网络、第三方、超时和限流错误
- 相关时的本地化、时区、货币、可访问性和响应式布局
- 变更行为周边的向后兼容性和回归区域

## 澄清策略

仅当缺失信息会实质性改变测试设计时才提问，例如角色规则未知、支持平台未知或关键业务约束不清楚。否则基于明确假设继续，并提供“问题 / 缺口”部分。

## 语言

匹配用户使用的语言。如果用户使用中文，除非用户要求英文，否则测试用例使用中文编写。
